## 2. 第二阶段交付什么

用户导入并完成必要读取核验后，系统自动整理明确重复；进入结果页即可看到去重后的流水、来源及处理依据。AI 处理本地难以判断但有实际价值的配对问题，结果经过约束检查才能影响统计。用户能纠正、撤销、暂不处理，并在追加账单后继续使用。

包括：

- 同来源导出区间重叠、跨批次重复记录；区别于第一阶段的同文件哈希拦截。
- 银行扣款与微信／支付宝描述同次付款时的跨来源去重，支持有证据的多订单合付。
- 直接、有依据的购买／退款关联；全退、部分退、多次退款及无原付款退款的保留。
- 本地规则、受保护的 AI 辅助配对、聚焦配对疑点的人工纠正。
- 明细、汇总、导出、解释、撤销、重算及重启保存的一致性。

暂不包括：本人账户身份工作台、亲友身份推断与管理、内部移动的个人收支剔除、借贷／理财／还款与生活支出分离、生活类别分类、私人背景报销和 AA 分摊、完整资产负债分析。一般转账原样留在去重流水中，不要求用户在本阶段回答其生活含义。

## 3. 先把“去重”和“配对”分清

| 场景 | 处理方式 |
| --- | --- |
| 同一来源两次导出含有同一笔付款 | 一个有效交易描述，保留两个批次的来源引用 |
| 银行扣款 100 元，微信订单支付 100 元，证据表明同笔付款 | 一次付款的多个来源，汇总只计一次，保留汇总两条记录的字段信息（如微信订单记录的字段信息对于后续分类有帮助，不能丢了）；不删除任何底稿 |
| 银行扣款 100 元，对应两笔 40 元、60 元订单，有明确合付依据 | 保留两笔订单及银行合付依据，付款合计仍为 100 元；不额外叠加银行 100 元 |
| 付款 100 元，后来退款 100 元 | 保留付款与退款两次真实收付，建立退款关联；不能将两行一起删掉或把收付总额都置零 |
| 银行扣款和另一账户入账，金额相同 | 不把相反方向的真实收付当成重复。是否属于本人内部转移留待后续身份／性质判断 |
| 交易时间金额相同，但存在多个可能付款对象 | 保留各记录，标注配对尚未确定，不强行合并 |

“真实流水”在本阶段具体指：在已导入、已可用范围内，合并有依据的重复描述后得到的交易视图。它不是对全部账户覆盖、全部交易完成去重或全部支出性质已确定的保证。

### 3.1 字段合并：金额只计一次，信息按字段保留

不能选一条银行流水作为唯一主记录，再把其余来源整体隐藏；也不能仅在归档底稿里保留微信内容，却让后续分类只读到银行摘要。合并后的结果必须直接提供可用的互补信息和来源引用。

例如，同笔 58 元付款已确认由微信订单与建行扣款共同描述：微信提供“某超市”、商品说明、“建设银行储蓄卡”支付方式、支付时间和平台订单号；建行提供“财付通”等渠道描述、记账时间、银行流水号和账户信息。结果计为一笔 58 元付款，展示具体商户及商品，同时保留银行侧资金依据。不能将“某超市”和支付机构名称简单认定为矛盾，也不能丢掉其中一方。

| 字段 | 合并规则建议 |
| --- | --- |
| 金额、币种、收付方向 | 作为计数与约束依据，不能挑选一个看似合理的值掩盖冲突；差异必须由明确合付分配等证据解释，否则不自动合并 |
| 支付对象／商户 | 保留不同来源原值及角色。具体商户可作主要显示；支付机构、结算主体和直接转账对象分别保留，不把所有名称压成一个字符串 |
| 商品、用途、摘要、备注 | 非空且有信息的内容互补保留，重复文本可合并显示，但来源引用不丢；不能用“消费”“转账”等通用摘要覆盖具体商品说明 |
| 支付时间、银行记账时间 | 按不同时间含义分别保留。主流水时间按明确、版本化的规则选择并标明来源，不能取平均或悄悄丢掉跨日记账差异 |
| 支付方式、渠道、资金账户 | 保留渠道与资金账户的区别；付款渠道可辅助匹配，不因此推断用户未确认的账户所有权 |
| 平台单号、商户单号、银行流水号 | 按来源及标识类型分别保存，不强行塞入一个“流水号”字段；为退款和后续分类保留可追溯标识 |
| 交易状态 | 保留来源原状态及语义。成功、关闭、退款等发生在不同层次，需解释一致性，不能机械用某一来源覆盖所有状态 |
| 账户余额 | 作为该账户该时点的来源属性保留，不相加、不跨账户拼成“合并余额”；识别不可靠标志继续有效 |
| 其他原始字段 | 无损保留在来源明细，未来新增用途可读取；本轮未标准化不等于无价值 |

字段选择遵循：同一来源先应用有效人工修订，再判断该字段的语义、具体程度与可靠性。空值、“未知”和低可靠识别不能覆盖有依据的有效信息；也不采用“微信永远优先”或“银行永远优先”的整体来源排序。内容更长不自动代表更准确。

合并结果采用三层信息组织：

1. **来源记录集合**：保留所有批次、原记录身份、有效修订版本与证据入口，不破坏原始行。
2. **面向用户的合并字段**：金额、主要交易对象、商品说明等可直接用于列表和后续处理。
3. **逐字段依据与备选值**：记录采用值来自哪些来源、为何采用、是否存在冲突；未采用值仍可追溯。第三阶段分类接口同时获得适用的商品／商户上下文，而不是只读取“主记录”的少数字段。

人工已确认的来源字段不能被合并时静默改回 OCR 原值。用户若纠正合并后的显示对象，应保存为可撤销的结果层修订，明确作用范围，不反向批量改写银行和微信底稿。来源更新后重新检查相关关系与字段选择，保留用户决定并标记需要复核的冲突。

一笔银行合付对应多个微信订单时，各订单的商品、商户及金额分别保留；共同银行来源通过分配关系引用，不把多个订单商品覆盖成最后一个，也不重复计算同一笔银行金额。退款关联同样保留退款自身字段，不用原付款信息覆盖退款事实。

本机完整字段保留与 AI 外发最小化是两层机制：本地数据不能为了脱敏被永久改成代号；发送给 AI 的副本按第 6 节处理，后续分类调用也需单独遵守其阶段范围。

## 4. 结果页与统计口径

首页以结果为主，默认按币种分开呈现去重后流出、流入及可追溯流水。提供原始来源笔数、当前交易笔数、已确认重复描述及尚待确定的配对数量。识别到的退款单列说明；不同币种不自动换算或相加。

- 普通流入不能直接叫工资／个人收入，普通流出不能直接叫生活消费。
- 疑似重复尚未确定时保留记录，并明确“该汇总仍可能包含重复计数”；不宣称最终精确结果，不为了数字好看而隐藏记录。
- 待读取核验、不可读批次继续沿用第一阶段的覆盖说明。配对待确认与读取待核验分别显示，避免混成同一种错误。
- 不将所有未知转账变成必答题。第二阶段的人工问题只围绕是否同笔、是否退款、是否错误配对等直接相关事实。
- 单条结果可展开各来源字段、系统采用的依据、冲突和人工处理历史；没有人工必选的“主来源”步骤。字段取舍需要来源追溯，关键冲突不得被静默覆盖。
- 页面、图表与导出使用同一有效结果层，不分别计算净额。原始来源明细入口继续保留。

退款遵循实际到账时间：9 月付款、10 月退款，分别留在各自月份。明确退款但未找到原付款时记为“退款／原付款未关联”。未来生活支出计算可据此使用当期退款抵减；第二阶段展示退款收付和关联说明，不推出生活支出净额。即使提供某次已关联付款的退款后金额，也明确为该付款详情，不冒充整本个人承担。

## 5. 自动判断、人工纠正与复用边界

从旧关系模块提取持久化、金额额度、输入版本、冲突检查、撤销和任务恢复能力；重新设计候选筛选及自动采用路径。不能把旧版全部候选确认一遍作为自动去重实现。

自动采用必须具备可追溯证据并通过约束。金额一致是主要条件，但同日同额、通用摘要、相似姓名和 AI 自报高分都不足以单独采用。强业务关联不能被机械短时间窗口否定；跨来源单号也不能在未验证标识命名空间时直接视为相同。

至少检查：币种、方向、交易状态及其来源语义、支付渠道、强业务标识、竞争匹配、已占用额度、共享退款额度、输入覆盖和候选搜索完整性。银行状态缺失不能机械等同于失败；关闭／撤销的订单也不能机械当成成功资金流，具体规则在实现前用真实字段分布与反例验证。

多订单合付、部分退款和多次退款使用金额分配及余额约束；同一笔资金不能重复被采用。退款本身也可能被多个来源描述，必须先保证退款金额不重复，再参与配对与汇总。

证据不足的候选不自动合并。人工可确认、拒绝、拆开已合并交易、暂不处理；纠正意图持久保存，重跑不立刻恢复已否决关系。新证据影响原决定时提示重新检查，不静默覆盖。

## 6. AI 辅助去重配对与隐私机制

第二阶段的 AI 只接收受控的配对上下文，输出候选关系、支持／反对证据和解释；不负责消费分类、亲友身份推断、个人承担决定或直接修改数据库。

| 数据 | 外发策略 |
| --- | --- |
| 用户姓名、账号、银行卡号、手机号、身份证号、地址等 | 本机识别并替换为同账本内一致的代号；原值和代号映射仅本地保存 |
| 直接转账对象的姓名、昵称、账号、联系方式 | 同样保护；同一对象保持必要的一致性，但不因姓名相似猜为同一人 |
| 普通商户、商品、金额、时间、渠道、交易类型 | 按去重配对所需保留，不为普通消费额外抹去有效业务线索 |
| 订单号、流水号等关联标识 | 用保留相等关系和来源命名空间的代号代替，避免泄露原始完整标识 |
| 摘要、备注、商品说明中的个人信息 | 无论属于消费还是转账，均先保护嵌入其中的个人信息；普通消费不等于可以外发其中的收货人和联系电话 |
| 原 PDF、Excel、截图、完整账号映射 | 默认不外发 |

代号按账本隔离，不使用可被枚举反推的裸哈希。保留原文映射的本地数据须随账本备份、删除与访问控制管理；本机隐私处理不等于声称已经不可逆匿名化。

流程建议：本地最小候选集合 → 字段白名单 → 私人对象与文本信息保护 → 出站检查 → 模型判断 → 结构校验 → 业务约束校验 → 采用／待确认／拒绝。个人身份不确定时采取保护默认，不要求用户先建联系人簿。无法可靠处理敏感字段时跳过该字段或该候选的外发，已有本地结果仍可用。

外发预览与日志也只展示处理后的载荷；服务错误和调试记录不能把原文或密钥写回日志。返回解释不得泄露本地映射；用户账单原文视为数据，不能当模型指令执行。模型无法改变证据政策、请求工具或自行扩大数据范围。

## 7. 增量处理与用户操作

- 本地处理随导入、核验修订和撤销自动检查受影响记录；保存输入修订、读取规则、关系策略等版本。
- AI 首版用“开始分析”触发，按需处理新增、变化或确有价值的未决候选；复用仍有效的既有结果，不每次全账本外发。
- 批量任务有真实进度、取消、失败重试和重启恢复；费用／条数达到配置上限时停止并说明未覆盖部分，不把截断候选当成唯一匹配。
- 输入更新时使受影响结果失效并重算；可展示历史结果但明确已过期，不能继续混入最新准确汇总。迟到的 AI 响应要核对原输入版本。
- 不在每笔 AI 建议前要求用户审批；符合证据和约束政策的结果可自动采用，用户能查看和纠正。点击开始分析前展示服务、数据范围与费用控制。

## 8. 分步实施与各步交付

| 步骤 | 主要工作 | 用户可验收的成果 |
| --- | --- | --- |
| B0 基线与关系底座审查 | 隔离复制验收数据，盘点来源字段／修订；检查旧模块可复用部分；先定义重复付款与退款的正反例 | 验收基线、来源覆盖、自动采用政策草案，明确已知盲点 |
| B1 规则去重与最小结果页 | 跨批重叠、强证据跨来源同笔；关系持久化与字段互补合并；结果明细／汇总／导出 | 不用确认全部候选，就能看到有依据且保留商户／商品等信息的去重流水；可以展开依据、纠正和撤销 |
| B2 配对与 AI 闭环 | 多订单合付、退款关联；隐私出站层；AI 候选、约束校验、增量任务与少量复核 | 合付和退款不重复计数，AI 只辅助配对；原付款缺失的退款清楚保留 |
| B3 整本持续使用验收 | 对五来源账本验证追加、修订、重算、撤销、重启；未参与调规则样本及隐私反例 | 结果、明细和导出一致；人工负担可接受，数据变化不会沿用过期结论 |

这些步骤是第二阶段内部的工程顺序，不把 B1 单独宣称为整个第二阶段已完成。B0 不扩张成另一轮大型手工标注工作台；只有缺少真值且影响判断的重要案例才请用户补充。
