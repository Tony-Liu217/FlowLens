# 来源字段完整性与银行表头差异

## 本次问题与修复

此前建行“交易地点/附言”已写入数据库的 `memo`，中行“附言”也已保存，但来源明细主要显示 `counterparty` 和 `description`，搜索也没有覆盖附言。这属于标准化与使用层衔接不完整，不能以“原文还在”作为验收通过的理由。

已识别的建行格式，现在将完整“交易地点/附言”作为缺失交易对方时的补充，并标注为“附言中的对方 / 渠道线索”。保留支付机构、渠道、商户等完整表达，不把其中任意一段猜成最终交易对象。原摘要继续独立保留。

已识别的中行格式，在摘要缺失时使用有效附言补充；交易名称、渠道、对方账户名分别保留。空白、横线等占位符不补成摘要。建行被遮蔽的“对方账号与户名”只保留来源证据，不尝试还原身份、不因遮蔽额外要求复核。

原有人工修订优先，包括明确保留的空值。新版规则通过读取层补充旧账本，原始底稿和历史事件不被改写，不需要重复导入。若人工确认过的空字段未自动填充，仍可在来源信息中看到附言线索。

## 面对新的银行格式

目前是通用文件读取、标准字段别名、已知格式规则与人工核验的组合，并非能理解任意表头的通用 AI。已知银行规则用于限定特定含义；不能把所有银行的“附言”都当作交易对方，也不能仅凭导入成功认定语义完整。

新增 `source_fields` 对每条已读取记录保存逐列标题、原值、映射目标和使用状态。未归类但有内容的列会出现在来源明细提示和文件读取结果中；原始字段表标明它尚未归类。所有保留字段均可检索，并随有效记录导出，供后续审阅和分析显式使用。备注、交易类型、支付渠道、来源分类及订单等已有语义字段可在明细展开查看。

这个检查证明的是“已经读取到的列有没有被归类”，不是证明整个文件没有漏页、OCR 没有漏字，也不是证明每个已匹配表头的实际含义正确。扫描件的原图与 OCR 证据仍需独立保留和核验。对于新格式，仍需抽查原文件、记录数、关键金额和语义字段；新列应在确认含义后增加有版本的映射规则及反例测试，不能直接凭关键词猜测。

“读取可用”表示通过当前金额、方向、日期等读取门槛，不代表交易对方身份已经核实，也不代表去重和个人支出分析已正确完成。未归类描述信息以非阻塞方式提示，避免让用户逐条处理不影响收支金额的辅助列。

## 验证方式

- 合成用例覆盖建行附言补充、中行摘要、未知表头保留、一般附言不推断身份、用户映射优先和人工空值保护。
- 使用实际建行 XLS、中行 PDF、微信 XLSX、支付宝 CSV 重新导入，并与现有五来源账本的隔离副本核对。
- 浏览器验收覆盖来源信息显示、未知列搜索、核验页说明及有效流水导出。

实际样本验证不构成所有银行格式的准确率承诺。后续的语义字段覆盖率、未知列数量和原始信息可追溯性，应与笔数、金额核对并列作为验收条件。
